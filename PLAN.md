# «Скрипт оператора» — план реализации

Внутренний инструмент отдела: за 30–60 секунд подобрать пациенту клинику и врача
под услугу (колоноскопия, гастроскопия, МРТ/КТ, профгигиена) с учётом его географии
и приоритетов отдела, и выдать готовый текст сообщения для отправки в мессенджер.

---

## 0. Вводные (зафиксировано по итогам обсуждения)

| Параметр | Решение | Следствие для разработки |
|---|---|---|
| Монетизация | **Нет.** Внутренний инструмент | Из скоринга убирается вся денежная логика |
| «Выгодная клиника» | **Ручной приоритет A/B/C** | Одно поле в карточке клиники, никаких формул маржи |
| Города | **Москва + Санкт-Петербург** | Два метро-графа, `city_id` во всех сущностях |
| Канал общения | **Только переписка**, оператор копирует текст сам | Достаточно кнопки «Копировать». Телефоны в системе не хранятся |
| CRM/телефония | Нет, сервис отдельный | Не нужны интеграции |
| Масштаб на старте | **Один оператор, тест** | **Админка не нужна в v1**, данные в таблице |
| Учёт доходимости | **Позже, не в v1** | Таблицы заложить в схему, UI не делать |
| МРТ/КТ | **По зонам и контрасту** | Справочник подвидов + быстрый поиск по синонимам |
| Врачи | **Только там, где важны** | Колоно/гастро/профгигиена → врач. МРТ/КТ → аппарат |
| Данные о врачах | Консолидация из нескольких источников | См. §6 — ключевая инженерная задача |

**Главная метрика:** время от «услуга названа» до «текст в буфере обмена». Цель ≤ 45 секунд.

## 1. Ключевое следствие: в v1 бэкенд не нужен

Раз нет монетизации, нет CRM, нет учёта статусов, нет команды и нет персональных
данных пациента — **весь сервис в первой версии это статичная SPA с JSON-каталогом.**

- Каталог (клиники, врачи, услуги, цены, тексты) — один JSON, собранный из таблицы.
- Метро, районы, координаты — офлайн-справочники в том же бандле.
- Поиск, фильтры, скоринг, сборка сообщения — целиком на клиенте.
- Никакой сети во время работы → ноль спиннеров, работает даже без интернета.
- Деплой — любая статика (или вообще локально открыть файл).

**Это сокращает срок с 5–6 недель до ~2,5 недель** и убирает целый класс проблем:
авторизацию, RLS, 152-ФЗ, хостинг Node, ключи API.

Supabase, роли и админка появляются в v2, когда операторов станет больше одного.
Схему БД проектируем сразу правильную (см. §8), чтобы переезд был импортом, а не переписыванием.

**Про 152-ФЗ:** так как телефон и ФИО пациента в систему не попадают вообще
(оператор копирует текст и вставляет в свой мессенджер), персональных данных
пациентов вы не обрабатываете. Это большое упрощение — не теряйте его случайно
в v2, добавляя «поле для телефона, чтоб удобнее».

## 2. Что вы упустили (главная ценность этого плана)

### 2.1. Противопоказания и подготовка — критично
Если оператор направил, а пациента развернули на месте — потеряны и пациент, и отношения с клиникой.

- **Колоноскопия**: подготовка (Фортранс/Мовипреп/Эзиклен), бесшлаковая диета 3 дня, отмена препаратов железа за 5 дней, антикоагулянты — согласование с врачом. Наркоз → нельзя за руль, нужен сопровождающий, не есть 8 часов.
- **Гастроскопия**: не есть 8 ч, не пить 4 ч. Трансназальная vs классическая — сильный аргумент для боящихся.
- **МРТ**: кардиостимулятор, ферромагнитные импланты, клипсы на сосудах мозга, инсулиновая помпа, кохлеарный имплант — **абсолютные противопоказания**. Вес и обхват (стол до 120–150 кг, туннель 60–70 см), клаустрофобия → нужен открытый аппарат. 1 триместр беременности.
- **КТ с контрастом**: аллергия на йод, креатинин/СКФ не старше 1–3 мес, метформин, беременность.
- **Профгигиена**: кардиостимулятор (ультразвуковой скалер), беременность, острый пародонтит.

**Решение:** экран-«светофор» из 3–6 вопросов, привязанных к конкретной услуге.
Оператор кликает чекбоксы за 10 секунд, система либо пропускает, либо переключает
фильтр (например «нужен открытый МРТ»), либо блокирует с готовым текстом отказа.

### 2.2. Седация/наркоз часто важнее адреса
Для колоно- и гастроскопии страх боли — фактор выбора №1. Наличие анестезиолога,
тип седации и цена «во сне» — отдельные поля и отдельный фильтр, а не строчка в описании.

### 2.3. Ближайшее свободное окно
Направили — а запись через 3 недели, и сделка сгорела. Нужны поля
`ближайшая дата` + `когда обновляли`. Данные старше 3 дней → карточка визуально
блёкнет и падает в сортировке. Без этого оператор будет уверенно обещать то, чего нет.

### 2.4. Отработка возражений
Скрипт — это не только «вот врач». Нужны быстрые ветки прямо на экране подбора:
«дорого» / «далеко» / «боюсь» / «я подумаю» / «а по ОМС?» / «у меня свой врач».
Это поднимает конверсию сильнее, чем красивая карточка.

### 2.5. Стоп-лист в один клик
Аппарат сломался, врач в отпуске, клиника не берёт — нужна кнопка «пауза»
на клинике/враче/услуге с причиной и датой. Иначе сутки шлёте в никуда.

### 2.6. Прочее, что закладываем сразу
- `city_id` во всех сущностях с самого начала.
- Дата актуальности цены — цены протухают быстрее всего.
- Быстрый поиск по подвидам МРТ с синонимами: «поясница» → «МРТ пояснично-крестцового отдела».
- Мобильная/планшетная вёрстка.
- Режим тренажёра для обучения новых операторов (когда они появятся).

## 3. Приоритет клиник и подбор

### Шаг 1. Жёсткие фильтры (исключают, а не штрафуют)
```
клиника активна и не на паузе
нужная услуга (подвид!) есть и активна
если нужен наркоз → есть седация и анестезиолог
вес пациента ≤ max_weight_kg аппарата
возраст ≥ min_age
если клаустрофобия → аппарат открытого типа
если нужен контраст → клиника делает с контрастом
город совпадает
```

### Шаг 2. Сортировка
Без денег формула становится честной и простой:

```
score = 100 × (
    0.35 × f_приоритет(A=1.0, B=0.6, C=0.3)
  + 0.30 × f_гео(время_в_пути_мин)        // clamp(1 − t/60)
  + 0.20 × f_окно(дней_до_записи)          // сегодня-завтра = 1.0
  + 0.15 × f_цена(относительно медианы)
)
− штраф, если слот или цена не обновлялись > 7 дней
```

Веса лежат в конфиге, редактируются в одном месте. Никакой админки для этого
в v1 не нужно — вы единственный пользователь.

### Шаг 3. Выдача — ровно 3 карточки
**«Рекомендуем»** · **«Ближе всего»** · **«Дешевле»**.
Первая всегда приоритетная для отдела, две другие дают, чем крыть возражения
«далеко» и «дорого». Четвёртый вариант — по кнопке «ещё».
Больше трёх карточек = оператор тормозит и выбирает наугад.

## 4. География: Москва и Санкт-Петербург

Три способа ввода в одном поле с автокомплитом:
1. **Станция метро** — покрывает ~90% случаев, офлайн, мгновенно.
2. **Район/округ** — центроид района.
3. **Произвольный адрес** — в v1 не делаем (нужен платный геокодер и сервер).
   Оператор спрашивает «какая станция вам удобнее» — это и естественнее звучит.

**Расстояние считаем как время в пути, не по прямой.** Прямая врёт: 2 км через
реку без моста — это 40 минут.

- Граф метро: станции + перегоны (~2,5 мин) + пересадки (~4 мин), поиск BFS.
- `walk_minutes` от станции до клиники заполняется один раз при заведении клиники.
- Итог: `время = BFS(станция пациента → станция клиники) + walk_minutes`.

Это даёт «до клиники 22 минуты» вместо бессмысленного «3,4 км» — и само по себе
становится аргументом в сообщении.

**Трудоёмкость:** справочники метро Москвы (~270 станций) и Питера (~72) с перегонами
и пересадками — это самая недооценённая часть проекта, закладываю на неё отдельные 2–3 дня.
Данные берутся из открытых наборов (данные Москвы / OSM), один раз проверяются руками.

## 5. Услуги: две модели продажи

Раз врач важен не везде — делаем **два типа карточки и два семейства шаблонов**.

**Врачебная модель** — колоноскопия, гастроскопия, профгигиена.
Главный аргумент: врач. Стаж, категория, количество процедур, «работает во сне»,
трансназальная методика, «объясняет каждый шаг».

**Аппаратная модель** — МРТ, КТ.
Главный аргумент: оборудование и сроки. Напряжённость поля (1,5 / 3,0 Тесла),
открытый или закрытый контур, модель томографа, срок выдачи заключения,
запись снимков на диск, возможность второго мнения.
Врач-рентгенолог упоминается опционально одной строкой.

**Справочник подвидов.** МРТ/КТ разворачиваются в ~40–60 позиций
(зона × с контрастом / без). Чтобы это не тормозило оператора:
- поиск по подстроке с синонимами и опечатками: «поясн», «спина», «шея», «голова»;
- топ-10 частотных подвидов — крупными кнопками сразу;
- остальное — через поиск.

## 6. Консолидация данных о врачах — как сделать правильно

Вы сказали: «хочется отовсюду тянуть, под капотом обрабатывать, консолидировать
и показывать в карточке единую инфу». Направление верное, но ключ здесь не в слиянии,
а в **происхождении и доверии к каждому факту**. Иначе вы получите красивую карточку,
в которой невозможно понять, откуда взялся «стаж 20 лет» и правда ли это.

### Модель данных
Две таблицы вместо одной:

- **`doctor_sources`** — по записи на каждый источник: выгрузка клиники, сайт клиники,
  агрегатор. У каждой: свой набор полей, дата сбора, сырой снапшот.
- **`doctors`** — «золотая запись», собранная из источников по правилам приоритета.

### Правила слияния полей
| Поле | Приоритет источников |
|---|---|
| ФИО, специальность | выгрузка клиники → сайт клиники → агрегатор |
| Категория, учёная степень | выгрузка клиники → сайт клиники (агрегатору не верим) |
| Стаж | самый свежий источник; расхождение >2 лет → пометка «конфликт» |
| Фото | только сайт/выгрузка клиники (право использования) |
| Кол-во процедур | только выгрузка клиники |
| Рейтинг, число отзывов | агрегатор — **внутренний сигнал, не для цитирования** |

### Матчинг «один и тот же врач в разных источниках»
Самая сложная часть. Ключ: нормализованное ФИО + клиника + специальность.
«Иванов И.И.» и «Иванов Иван Иванович» в одной клинике по одной специальности —
одно лицо. Всё, что не сматчилось однозначно, падает в очередь на ручное подтверждение,
а не склеивается автоматически. Ошибочная склейка двух врачей хуже, чем её отсутствие.

### Провенанс в интерфейсе
У каждого факта в карточке — источник и дата: «стаж 20 лет · сайт клиники · 12.08».
Оператор сразу видит, чему можно верить, и не озвучит пациенту протухшую информацию.

### Жёсткое правило для текста сообщения
В сообщение пациенту попадают **только поля со статусом «подтверждено»**
(выгрузка клиники или ручная проверка человеком). Остальное живёт на экране
оператора как справка, но не уходит пациенту. Это защищает вас от обещания того,
чего нет.

### Отдельно — про рейтинги с агрегаторов
Собирать можно, но использовать в сообщении пациенту («рейтинг 4.9 на ПроДокторов»)
не стоит: чужой контент, чужая товарная марка, и отвечать за это придётся вам.
Практичнее: рейтинг = **внутренний сигнал сортировки**, а пациенту называем
проверяемые факты. «Выполнил более 8 000 колоноскопий» убеждает сильнее,
чем «4,9 звёзд» — и это ваш факт, а не чужой.

### Честная рекомендация по срокам
**Для 20 клиник парсеры писать дороже, чем заполнить таблицу руками.** Реально:
день работы против недели разработки. Поэтому:

- **v1** — заполняем руками в таблицу, но **по структуре, спроектированной под многоисточниковость** (поля `источник` и `дата проверки` у каждого блока фактов).
- **v2** — добавляем импорт с сайтов клиник, когда клиник станет 50+.
- **v3** — агрегаторы, если к тому моменту это всё ещё будет нужно.

Схема не меняется ни на одном шаге — меняется только способ наполнения.

- Копирование подтверждается заметной галочкой — оператор не должен гадать, сработало ли.

## 8. Схема данных

В v1 это структура JSON-каталога; в v2 — те же таблицы в Postgres/Supabase
(uuid PK, `created_at`, RLS). Проектируем один раз.

**Гео**
- `cities` (id, name)
- `metro_stations` (id, city_id, name, line_name, line_color, lat, lng)
- `metro_edges` (station_a, station_b, minutes)
- `districts` (id, city_id, name, center_lat, center_lng)

**Услуги**
- `services` (id, code, name, model `doctor|equipment`, hotkey, sort)
- `service_variants` (id, service_id, name, synonyms[], with_contrast, is_popular)

**Клиники**
- `clinics` (id, city_id, name, address, lat, lng, phone, work_hours, priority_tier `A|B|C`, is_active, paused_reason, paused_until, notes_internal, updated_at)
- `clinic_metro` (clinic_id, station_id, walk_minutes)
- `clinic_services` (id, clinic_id, service_variant_id, price, price_sedation, duration_min, has_sedation, has_anesthesiologist, equipment_model, tesla, mri_type `open|closed`, max_weight_kg, min_age, report_hours, nearest_slot_date, slot_updated_at, price_updated_at, is_active)

**Врачи** (см. §6)
- `doctors` (id, clinic_id, full_name, specialty, photo_url, experience_years, category, degree, education, procedures_count, bio, confidence `confirmed|unverified`, is_active)
- `doctor_services` (doctor_id, service_variant_id)
- `doctor_selling_points` (id, doctor_id, type, text, confidence, sort)
- `doctor_sources` (id, doctor_id, source_type, payload jsonb, checked_at)

**Контент**
- `message_templates` (id, service_id, model, tone, body)
- `objections` (id, service_id, label, answer, sort)
- `prep_instructions` (id, service_variant_id, title, body_md)
- `contraindications` (id, service_variant_id, severity `absolute|relative`, question, block_text, redirect_hint)

**Задел на v2 (структура есть, UI нет)**
- `referrals`, `referral_events`, `profiles` — для учёта доходимости и команды.

## 9. Пример сообщения

**Колоноскопия, врачебная модель, тревожный пациент**

> Мария Сергеевна, подобрали для вас вариант рядом — клиника «Мед-Плюс»
> на Автозаводской, 6 минут пешком от метро.
>
> Колоноскопию проводит Иванов Иван Иванович: 20 лет практики,
> врач высшей категории, выполнил более 8 000 исследований.
> Процедура во сне, под контролем анестезиолога — вы ничего не почувствуете
> и проснётесь, когда всё уже закончится.
>
> 12 400 ₽ — вместе с седацией и гистологией одного участка.
> Ближайшее окно: четверг, 14:30.
>
> Забронировать за вами? Памятку по подготовке пришлю следом.

**МРТ, аппаратная модель**

> Нашли центр в 6 минутах от Автозаводской — МРТ-центр на Автозаводской.
>
> Томограф Siemens Magnetom 1,5 Тесла, стол до 130 кг.
> Заключение отдают через 40 минут, снимки записывают на диск бесплатно —
> ехать второй раз не придётся.
>
> МРТ поясничного отдела — 6 400 ₽. Ближайшее время: завтра в 10:20.
>
> Записать вас?

**Как это устроено:** шаблон с плейсхолдерами + 3 тезиса, выбранных по услуге
и заявленной тревоге пациента. Тональности: спокойный / тревожный / «дорого» /
пожилой / деловой (короткий). Плюс отдельная кнопка «скопировать памятку по подготовке» —
она заметно повышает доходимость и выглядит как забота.

**Линтер текста:** перед копированием проверяем на формулировки, которые нельзя
использовать в медицинской рекламе (ФЗ-38 ст. 24): гарантии результата, «лучший»,
«№1», «абсолютно безопасно». Подсветка прямо в редакторе.

## 11. Этапы

**Э0. Данные (параллельно всему, начинать сразу)**
Расширить вашу таблицу клиник до нужной структуры: метро + минуты пешком, подвиды
услуг с ценами, параметры аппаратов, наличие седации, приоритет A/B/C.
Отдельные листы — врачи, тезисы, возражения, подготовка, противопоказания.
Дам готовый шаблон таблицы первым делом.

**Э1. Каркас и справочники — 3–4 дня**
Vite + React + Tailwind, сборка каталога из таблицы, валидатор,
метро-графы Москвы и Питера, расчёт времени в пути, тесты на `metro.js`.

**Э2. Подбор — 3–4 дня**
Фильтры, сортировка, три карточки, выбор услуги и подвида с поиском по синонимам,
горячие клавиши. Тесты на `ranking.js`.

**Э3. Карточки и сообщения — 3 дня**
Две модели (врач / аппарат), банк тезисов, шаблоны, тональности, линтер, копирование.

**Э4. Медицинский слой — 2 дня**
Скрининг противопоказаний, памятки подготовки, шпаргалка возражений.

**Э5. Полировка и запуск — 2 дня**
Скорость, мобильная вёрстка, деплой статики, инструкция на одну страницу.

**Итого: ~2,5 недели.**
**Кликабельный прототип главного экрана на 10 захардкоженных клиниках — 2 дня**,
и его стоит сделать первым: потрогать, понять, что реально мешает, и только потом
строить справочники.

## 12. Что делаем в v2 (когда операторов станет больше)

Порядок по убыванию пользы:
1. **Учёт результата** — статусы «согласился / отказ / думает», статистика по клиникам и формулировкам. Без этого вы не узнаете, какие тезисы работают.
2. **Supabase + роли** — общие данные, авторизация, несколько операторов.
3. **Админка** — редактирование клиник, цен, врачей и шаблонов без правки таблицы.
4. **Импорт данных о врачах** с сайтов клиник (см. §6).
5. **Геокодер** для произвольных адресов, если станций перестанет хватать.
6. **Режим тренажёра** для новых операторов.
